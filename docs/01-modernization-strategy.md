# 现代化策略

## 1. 要现代化的到底是什么

原版是 2003 年的 **DirectDraw 软件 blit** 引擎，逻辑分辨率固定，输入完全围绕鼠标：左键移动/攻击、右键技能、按住 Alt 划轨迹切换必杀技。

所以"现代化"其实是四件互相独立的事：

| 维度 | 现状 | 目标 |
| --- | --- | --- |
| 显示 | 定分辨率、定帧率、后处理靠外部兼容层 | 任意分辨率、高刷、整数缩放 |
| 输入 | 鼠标手势，无缓冲概念，无手柄 | 手柄优先、输入缓冲、可视化映射 |
| 数据 | 纯文本表，但无编辑器、无 schema | 结构化、可校验、可视化编辑 |
| 内容 | 正传与外传各自独立 | 单一入口、章节串联 |

四件事的耦合度很低 —— 这决定了可以**分头推进**，不必等一个大重写。

## 2. 两条路线

### Track A · 外挂式现代化

保留 `ComeOn.exe`，通过注入与外部工具改造：

- DLL 注入 + 函数 hook：输入重写、帧率解锁、HUD 重排
- 外部编辑器：直接读写 `bdh\<lang>\*.txt`
- 资产替换：解包 → 改图 → 重打包

**优点**：立刻能玩，资产零转换，风险可控，每一小步都能验证。
**缺点**：受制于 2003 年的逻辑分辨率、硬编码 UI 布局、脆弱的内存布局。

### Track B · 重制

用 M1 导出的资产 + M2 的数据在 Godot 4 里重新实现。

**优点**：唯一能真正达成"双作合一 + 手柄 + 可视化连招编辑器"的路径。
**缺点**：工作量以人年计，最大风险是**手感跑偏** —— 而手感恰恰是这游戏的全部价值。

### 结论

> **A 先行，B 为主线，A 的真正价值是为 B 提供 ground truth。**

外挂改造不只是"能玩就行"：一旦能 hook 到战斗状态机，就能**把原版当成 oracle 去采样**——给定输入序列，记录每一帧的招式 ID、判定、硬直、浮空高度。这份数据就是重制版的验收标准。

没有这份数据，B 只能靠"感觉像"，而"感觉像"在格斗游戏里等于失败。

## 3. 目标架构

```
┌────────────────────────────────────────────────────┐
│  rekit（静态）        │  bridge（动态）              │
│  容器解析 / 导出      │  注入 / hook / 事件日志       │
│  数据表 ↔ JSON        │  输入拦截 / 帧采样            │
└──────────┬───────────┴───────────┬────────────────┘
           │ 资产 + 数据 + 日志      │ 实时状态
           ▼                       ▼
┌──────────────────────┐   ┌──────────────────────┐
│  editor（编辑器）     │   │  runtime（重制版）    │
│  连招 / 数值 / 图集   │   │  Godot 4             │
│  共享同一套 schema    │   │  输入层 + 战斗状态机  │
└──────────────────────┘   └──────────────────────┘
```

关键约束：**`rekit` 与 `editor` 共用一份 schema 定义**。数据表的列语义只写一次，导出、校验、编辑、导入全部读它。否则四个工具会各自漂移。

## 4. 输入层设计要点

原版的必杀技是**鼠标轨迹**：按住 Alt 画出对应轨迹。手柄没有"轨迹"，只有摇杆。

三种映射方案：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| 径向轮盘 | 按住 LB 弹出 8 向轮盘，右摇杆选方向 | 直观、易发现、无学习成本；但打断战斗节奏 |
| 摇杆描迹 | 按住 LB 时记录右摇杆轨迹，与模板做形状匹配 | 最接近原版手感；需要调匹配阈值 |
| 招式槽 | 直接把手柄按键绑定到固定招式 | 最简单，但丢掉了"画招"的核心体验 |

建议：**默认摇杆描迹，轮盘作为无障碍备选**。描迹用"重采样到固定点数 + 余弦相似度"即可，不必上复杂识别。

另一个必须做的：**输入缓冲**。原版没有缓冲概念，导致输入必须在帧边界精确命中。现代化版本应引入 6–10 帧的输入队列，这是"手感变现代"最廉价、最有效的一步。

## 5. 连招编辑器的数据模型（草案）

```text
Action      一次出招：动作 ID、总帧数、起始帧、结束帧
Segment     帧区间 + 判定框 + 伤害类型（戳刺/猛砍/剁削/跳劈/躲闪/格挡）
Cancel      取消窗口：从第 a 帧到第 b 帧，可被哪些 Action 打断
Chain       序列：Action 的有序/自由组合（对应 Role.txt 的"先后序列"/"自由序列"）
Condition   进入条件：前置招式、命中/落空、硬直剩余、浮空高度
```

这套模型能完整表达原版 `Role.txt` 的 47 列语义，并且是**可可视化**的：时间轴上的色块 = Segment，色块之间的箭头 = Cancel。

## 6. 双作合一

两作的表结构高度相似（外传是正传的超集：新增角色、新增地图、扩展物品）。合并策略：

1. 以**外传为基**（数据更全），正传作为"章节包"挂载；
2. ID 命名空间加前缀（`v1_` / `v2_`），避免同名冲突；
3. 存档迁移层负责把两边的存档映射到统一 schema。

## 7. 边界

- 不重制美术。原版是预渲染像素图，重画成本过高且必然失真。
- 不改战斗数值平衡。只做"可编辑"，不做"我觉得这样更好"。
- 不分发资产。仓库只有工具与文档，资产由使用者本地生成。
