## 2. 引用编码（终于确定）

之前我一直把 ref 的高位当成"标志位"。`FUN_00505750` 把它讲清楚了：

```c
void FUN_00505750(void *this, uint ref, uint *outIndex, int *outLib) {
    *outIndex = ref & 0xff0fffff;              // 清掉 bits[23:20]
    *outLib   = FUN_00505780(this, (ref >> 0x14) & 0xf);   // bits[23:20] = 库下标
}
```

所以一个 32 位引用是：

```
bit 31..24   帧序号（同一帧包内第几帧，0 = 第 0 帧）
bit 23..20   库下标（0..13，顺序同 idx.lib）
bit 19..0    库内条目号
```

对照 `Spr#901`（剑客）的第一条记录 `ref = 0x00101737`：

- 库下标 = `(0x00101737 >> 20) & 0xF` = **1** → `Res00`
- 条目号 = `0x00101737 & 0xff0fffff` = `0x1737` = **5943**
- 所以指向 **`Res00#5943`**，后续 47 条依次是 5944、5945……

`Res00#5943` 确实存在（10288 字节，`lep\0` 开头，16bpp）。之前我按"低 20 位当全局号"
算出的 `Res00#4153` 是错的。

## 5. 精灵块的排布：每动作 64 条

`ResPlayer1` 的已解析区间呈现明显的 **64 步长**：

```
0-51  |56-57|  60-115  |120-121|  124-179  |184-185|  188-243  |248-249|  252-307 ...
        ↑                 ↑                  ↑                  ↑
      60                124                188                252   ← 每 64 起一块
```

即每个动作占 **64 个条目**，实际按需加载其中 56~58 条。

而 `Role.txt` 里剑客的动作基址是 `0 / 16 / 48 / 80 / 112 / 352 / 384 / 400`（16 的倍数），
`预读动画` 是 `16 32 48 64 80 96 112 128 144 176 192 208 240 256 288 304 320 336`。
两者都能被 16 整除，说明"动作基址"至少是**帧组内的步进**，而不是 64 对齐的块首。

### 条目里的帧数

实测 `ResPlayer1` 前 18 条的帧数：

## 6. 顺带修掉的解码 bug

`lep.py` 的 `canvas_bytes` / `width_check` 在累加 `count` 时**没有做边界钳制**，而
`runs()` 有。某一行尾部的坏 run 会让宽度膨胀几个数量级（`Res00#5943` 被算成
119631 px 宽），`contact_sheet` 因此把它缩成 1px，看起来"整张全透明"。

已改成和 `runs()` 同一套钳制逻辑。

### 但 `Res00#5943` 仍有未解之谜

- 文件 10288 字节，行表按 `offsets[0]/4 = 53` 行、末行偏移 4008，行数据只用到 `0xFD8`；
- 可 `0xFD8` 之后还有 6232 字节，而且开头的 `14 00 38 00 01 02 02 …` 和**第 0 行同构**
  （gap=20, count=56）；
- 整个条目里只有 **1 个** `lep\0`。

也就是说这类角色图可能不是"一张图 + 行表"，而是"行表只覆盖前半段、后半段是另一块
同构数据（掩码？第二个朝向？）"。**这是下一个要解的格式问题**，解开之后
`Res00` / `ResPlayer1` 里所有角色图就能批量出图了。

## 7. 分层绘制锚点：找到了

这是之前一直缺的那一环，现在从代码 + 运行时两边对上了。

### 代码：绘制偏移就是"锚点减裁剪原点"

`FUN_0050b3f0`（取一次绘制的位置与尺寸）与 `FUN_0050b440` / `FUN_0050b4b0`（真正下笔）
里出现同一个表达式：

```c
x = ((int)*(short *)((int)this + 0x0e) - (int)*(short *)((int)this + 0x12)) + 传入的 x;
y = ((int)*(short *)((int)this + 0x10) - (int)*(short *)((int)this + 0x14)) + 传入的 y;
w = *(int *)(FUN_0050cd10(this) + 0x0c);      // 尺寸从被引用的图对象上取
h = *(int *)(FUN_0050cd10(this) + 0x10);
```

也就是说**每一层子图都自带一个 4 个 short 的定位信息**：

```
+0x0e  锚点 X        +0x12  裁剪原点 X
+0x10  锚点 Y        +0x14  裁剪原点 Y
        → 相对实体的绘制偏移 = (锚点X − 裁剪X, 锚点Y − 裁剪Y)
```

这正是"帧被紧裁过、但引擎仍能摆对位置"的答案：**偏移不在 lep 里，在引用它的那个
22 字节槽位里**。

### 运行时实测：一帧 = N 个 22 字节槽位

扫描 vtable `0x005541AC`（`FUN_0050b3b0` 构造的就是这个类）得到连续 7 个槽位，
步长 `0x16 = 22` 字节：

```
blk0 @041091B4 vt=005541AC +4=1313 +8=0EB209D4(=Res00描述符) +C=2  shorts(C,E,10,12,14)=(2,0,0,35,23)  offset=(-35,-23)
blk1 @041091CA vt=005541AC +4=1314 +8=0EB209D4                    shorts=(2,0,0,35,22)  offset=(-35,-22)
blk2 @041091E0 vt=005541AC +4=1315 +8=0EB209D4                    shorts=(2,0,0,35,24)  offset=(-35,-24)
blk3 @041091F6 vt=005541AC +4=1316 +8=0EB209D4                    shorts=(2,0,0,34,24)  offset=(-34,-24)
blk4 @0410920C vt=005541AC +4=1317 +8=0EB209D4                    shorts=(2,0,0,34,23)  offset=(-34,-23)
blk5 @04109222 vt=005541AC +4=1318 +8=0EB209D4                    shorts=(2,0,0,34,23)  offset=(-34,-23)
blk6 @04109238 vt=005541AC +4=1319 +8=0EB209D4                    shorts=(2,0,0,35,23)  offset=(-35,-23)
```

槽位布局：

| 偏移 | 含义 |
| --- | --- |
| `+0x00` | vtable `0x005541AC` |
| `+0x04` | 被引用条目在库内的**本地下标**（1313..1319，逐个 +1） |
| `+0x08` | 被引用条目的**库描述符**（这里全是 `Res00`，即 `0x0EB209D4`） |
| `+0x0C` | `short`，来自源记录 `[1]`（这里恒为 2） |
| `+0x0E` / `+0x10` | 锚点 X / Y（这里恒为 0） |
| `+0x12` / `+0x14` | 裁剪原点 X / Y（35,23 上下浮动 1~2 px） |

> 注意 `+0x04` 是**库内下标**，不是全局号——和 `idx.lib` 那套全局编号是两回事，
> 槽位里同时存了库指针，所以不需要全局号。

同一套扫描换成"`+0x08` == `ResPlayer1` 描述符（`0x0EB21BF4`）"来过滤，也能拿到大量
同类槽位（`0x041B6034`、`0x041B9014`、`0x041BF034` …），说明**玩家自己的每一层也是这种
槽位**，只是分布在别的结构里。

需要如实说明的一点：`ResPlayer1` 那批槽位里 `+0x12` 常读到 `65523`（即 `-13`），
`Res00` 那批则是 `35 / 23` 这种正常值。两种可能——要么 `+0x12` 是有符号裁剪量、
要么这批槽位当时还没填完整。**这 4 个 short 的确切语义（哪个是锚点、哪个是裁剪、
符号方向）还没有定死**，但"绘制偏移 = 两组 short 相减"这一点是代码里写死的。

### 帧原始数据的格式（`FUN_0050b710` / `FUN_0050b5a0`）

```
u16 frameCount
每帧:
    u32 nSub            // 这一帧由几个子图组成
    u32 ?               
    u32 strideInts      // 每个子图占 7 个 int（28 字节），这里通常是 7
    子图 × nSub:
        u32 flag        // 0 = 有自己的 surface
        u32 ?           
        u32 数据/引用    // 交给 FUN_0050cd30 去解析出 (库, 下标)
        u32 A           -> 槽位 +0x0e（锚点 X）
        u32 B           -> 槽位 +0x10（锚点 Y）
        u32 C           -> 槽位 +0x12（裁剪 X）
        u32 D           -> 槽位 +0x14（裁剪 Y）
```

所以**"一帧有几层"是显式记录的**（`nSub`），每层都有自己的锚点/裁剪和图片引用。
之前困扰很久的"角色是怎么合成的"，机制到这里就完整了。

## 8. 组合表就是 `Spr` 条目本身（闭环）

上面那套"22 字节槽位"不是凭空来的，它正是 `Spr` 条目在内存里的展开形态。
用同一个格式去读文件，`Spr#901`（剑客 初始态）一次就解开了：

```
Spr#901  size=1924  →  (count=48, frame0 nSub=1, stride=7)
  f0   Res00#5943  off=(-36,-26)  A,B=(0,0)  C,D=(36,26)
  f1   Res00#5944  off=(-33,-29)  A,B=(0,0)  C,D=(33,29)
  f2   Res00#5945  off=(-28,-31)  A,B=(0,0)  C,D=(28,31)
  f3   Res00#5946  off=(-22,-31)  A,B=(0,0)  C,D=(22,31)
  f4   Res00#5947  off=(-21,-30)  A,B=(0,0)  C,D=(21,30)
  … 共 48 帧
```

所以之前看到的"每条记录 40 字节 = `[1,4,7,0,4,ref,0,0,a,b]`"其实是：

```
u16 frameCount(48)
每帧:  u32 nSub=1   u32 ?=4   u32 stride=7      ← 12 字节帧头
每子图: u32 flag    u32 ?    u32 ref           ← 7 个 dword = 28 字节
        u32 A(锚点X) u32 B(锚点Y) u32 C(裁剪X) u32 D(裁剪Y)
帧步长 = (stride*nSub + 3) dword = (7*1+3)*4 = 40 字节  ✓ 与实测一致
```

`A,B` 恒为 0、`C,D` 就是之前那串 `36,26 → 33,29 → 28,31 …` 的数值。
按 `FUN_0050b3f0` 的公式，**绘制偏移 = (A−C, B−D) = (−C, −D)**。

也就是说：角色站在实体点上，每一帧的图按"裁剪原点取负"贴回去——这正是紧裁帧
还能对齐的原因，而且**每帧自己的裁剪原点就是它的对齐信息**。

另一条交叉验证：`Spr#145` 是 `1 帧 × 7 子图`，引用 `Res00#1313..1319`，偏移
`(-35,-23)` 上下浮动；而运行时在 `0x041091B4` 找到的那 7 个槽位，正是它
（`+0x04 = 1313..1319`、`+0x08 = Res00` 描述符、short `(2,0,0,35,23)`）。
**文件 → 内存 → 槽位 → 绘制公式，四段全部对上。**

`FUN_0050cd30` 的代码也印证了这点：

```c
FUN_00505750(&DAT_00591e18, ref, &index, &libDesc);   // ref 拆成 (库, 库内下标)
FUN_0050cd70(this, index, libDesc);                   // 存进槽位
```

槽位里存的是**完整 ref**，不是索引，所以解析时用同一个 `FUN_00505750`。

### 格式已钉死：1786/1786 条精确对齐

把上面这套解析器跑遍整个 `Spr` 库，**1786 条组合表全部恰好消费完整条目字节**
（`4 + Σ(12 + nSub*stride*4) == entry size`），0 条对不上。这不再是推测。

同类样本（注意 `nSub` 个层引用的常常是**同一个帧包的不同帧号**）：

```
Spr#896: 16 帧 × 4 层, 全部 ref ResNpc2#2342, 帧号 1,2,3,2
Spr#902: 88 帧 × 4 层, 全部 ref ResNpc2#2350, 帧号 1,2,3,2
Spr#906:  8 帧 × 6 层, 全部 ref ResNpc2#2440, 帧号 1,2,3,4,3,2
```

### 三个库的分工（全库分类）

| 库 | 条目数 | 组合表 | 帧包 | `lep` 单图 | 其他 |
| --- | --- | --- | --- | --- | --- |
| `Spr` | 1790 | **1786** | 0 | 0 | 4 |
| `ResPlayer1` | 5248 | 0 | 2421 | 0 | 2827 |
| `Res00` | 14341 | 0 | 0 | 10136 | 4205 |

即 `Spr` = **动作/组合层**，`ResPlayer1` = **角色帧包层**，`Res00` = **图像层**，
正好对应 `FUN_005051e0` 里的"单图 / 帧包"两种类型。

### 一个还没解释的现象：`图形ID = 901` 指向的是光效，不是身体

`Spr#901` 的 48 帧每帧只有 1 层，引用 `Res00#5943..5990`。把那 48 张图解出来
（38×53、8 位渐变、值 `1..14` 平滑变化），是一个**旋转的光斑/刀光**，不是角色立绘。

而 `Role.txt` 里剑客的 `光影效果 = 1`、`图形ID = 901` 是两个不同的列。
所以现在有两种可能，**都还没排除**：

1. `图形ID` 对玩家角色不是身体来源（身体来自 `ResPlayer1` 的 899 条），
   `901` 这条只是给某种效果用的；
2. 我对 `图形ID` 列的定位错了（虽然 250/250 都落在 `Spr` 区间内，看起来不像）。

NPC 侧样本更"正常"：`Spr#896/902/906` 引用的都是 `ResNpc2` 的帧包，
符合"组合表 → 帧包 → 图像"的层级。

## 9. `lep` 的末行问题：已解决（解码层面）

`Res00#5943`：文件 10288 字节，行表 `offs[0] = 212` → 53 行，`offs[52] = 4008`，
行数据只到 `0xFD8`；可文件一直到 `0x2830`，多出 6232 字节。

原因是**最后一行没有下一行偏移来界定**，解析时把后面那 6232 字节也吞进了最后一行，
于是一行的 `count` 读到天文数字、画布宽度膨胀到 119631 px，图被缩成 1px。

修法：先只用前 `n-1` 行算画布宽度，再把每一行（含末行）的游程遍历**限制在画布宽度内**。
修完之后 `Res00#5943` 的 53 行宽度**全部一致 = 76 字节（38 px）**，出图正常。

顺带纠正一个旧结论：`lep` 的行宽**不一定恒定**。等距菱形图（如 `Res00#1`）每行
宽度按 4 字节递增/递减（68/72/76/80），所以"每行总宽相等"只能当"不超过画布宽"用。

那 6232 字节到底是什么（掩码？第二朝向？调色板？）仍未确定，但不影响解码。

## 10. 端到端重建成功（附成品图）

新增 `tools/rekit/render_composite.py`：直接从库里读一条组合表 → 逐帧逐层解析 ref →
取对应帧包的对应帧 → 按 `(A−C, B−D)` 叠到共同画布上。**不需要游戏**。

三条独立验证过的样例：

| 条目 | 内容 | 结果 |
| --- | --- | --- |
| `Spr#896` | 16 帧 × 4~8 层，ref `ResNpc2#2342` 帧包 | 一个穿蓝袍的完整 NPC，8 个朝向 + 影子，拼接无错位 |
| `Spr#34` | 512 帧 × 7~10 层，ref `ResPlayer1` | 剑客的**腿**，8 个朝向 × 2 姿势 |
| `Spr#901` | 48 帧 × 1 层，ref `Res00#5943..5990` | 一把**旋转的刀光/剑气**，不是身体 |

### 角色是怎么"合成"的——最终答案

一个角色**不是一条组合表**，而是**若干条 `Spr` 条目，每条一个身体部件**：

- `Spr#34` = 腿
- `Spr#35` / `#112` / `#113` / `#161`… 各自是别的部件（尺寸 14×18、47×17、52×18 各不相同）
- 每条条目内部：`帧 × (nSub 层)`，每层 = `ref + (A,B,C,D)`

`Role.txt` 里剑客的 `属性` 列是 `001*001*005*000*000*000*000*005*001`（9 个数字）,
很可能就是这套部件列表，还没验证。

`Spr` 里引用 `ResPlayer1` 的条目一共 **82 条**，就是玩家角色的全部动作表；
本次场景运行时被解析的是 `112-113 / 165-166 / 171-174 / 177-184` 这几组。

### 512 帧时间轴

这 82 条里，凡是真的引用帧包的（60 条）有一个共同点：**帧数都恰好是 512**，
而且层数分布完全一致（`1x32, 2x48, 3x32, 4x16, 5x16, 6x48, 7x52, 8x100, 9x32,
10x40, 11x32, 12x16, 13x32, 14x16`，合计 512）。

而 `Role.txt` 里剑客的动作基址全部落在 `0..511`：

```
初始态 0 / 平休1 16 / 平时走路 48 / 跑步 80 / 硬直 96,144 / 挨打 112
浮空 128 / 防守 352 / 起身 384 / 死亡 400
预读动画 16 32 48 64 80 96 112 128 144 176 192 208 240 256 288 304 320 336
```

所以 **一个条目 = 一个身体部件在整条 512 帧动作时间轴上的图层**，
`Role.txt` 的动作基址就是这条时间轴上的位置。这一点基本可以确定。

### 还没打通的一环：条目 × 帧号 到 (部件, 朝向, 动作) 的映射

我试过把 60 条部件表在同一个帧号上叠起来 → 600 层、画布炸到 65566×65543
（原因是 `A..D` 是**有符号** 16 位，`65531` 实际是 `-5`；这个已修）。

修完再用"引擎当时真正解析过的那 16 条"在帧 0 合成，得到的是**错位叠影**：

![错位叠影](out/shots/char_live.png)

说明这些条目的帧号**不是同一个朝向/动作**。单条 `Spr#177` 按 32 帧步进抽样，
看到的是**手臂的不同姿势**（不是 8 个朝向按 64 步进）：

![Spr#177 步进](out/shots/spr177_steps.png)

所以还差一步：**引擎在画角色时，每个部件实际用的是 (条目, 帧号) 是多少**。
这只能从运行时拿——找到持有这些部件表的那层结构，读它当前的下标。

`lep` 侧、组合表侧、偏移公式侧都已经关闭，这是最后一块拼图。

## 10. 复现命令

```powershell
cd tools\rekit

# 读管理对象 / 描述符 / 缓存（需要 CE 已经打开进程）
python ce_read.py --pid <pid> read-dwords 0x00591E18 8
python ce_read.py --pid <pid> read-hex   0x04144D70 96

# 组合表解码（帧 -> 层 -> 引用 + 偏移）
python scan_composite.py --lib Spr --limit 200 --show 3

# 单张 lep 的行表探针
python lep_probe.py --lib Res00 --entry 5943 --rows 3

# 联络表
python contact_sheet.py --lib ResPlayer1 --start 0 --count 64 --out ..\..\out\shots\rp1_0.png
```
