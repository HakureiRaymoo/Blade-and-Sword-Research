# 组合库（CombineLib）与精灵描述表

这一篇记两件事：**失焦暂停的实测结论**，以及本轮的真正突破——`zy/idx.lib` 定义的
**全局条目编号空间**，它推翻了此前"`Role.txt` 的图形ID 指向 `ResPlayer1.lib`"的假设。

---

## 1. 失焦暂停：已实测确认

工具：`tools/rekit/capture_window.ps1`（GDI `BitBlt(GetWindowDC)`）+ `tools/rekit/bg_probe.py`

同一场景（南方面地图、主角站立待机），连拍 3 帧、间隔 0.7–0.9 s，逐像素比对：

| 状态 | 平均绝对差 | 变化像素数 |
| --- | --- | --- |
| 游戏**非**前台（前台是别的窗口） | `0.0000` | **0** |
| 游戏前台 | `23.56` | **640 407** |

3 帧完全逐字节相同，所以不是"变化太小没看出来"，是真的停住了。

### 处置方案

`cnc-ddraw` 有一个正是为此存在的开关：

```ini
; ddraw.ini  —— 已加到 [comeon] 段（游戏内置预设已经有 maxgameticks=60 / fixchilds=3）
noactivateapp=true
```

它让 cnc-ddraw 在 `PeekMessage`/`GetMessage` 层面**吞掉 `WM_ACTIVATEAPP` 与
`WM_NCACTIVATE`**，游戏于是永远认为自己在前台。

> 该选项只在进程启动时读一次，改完必须重启游戏才生效。备份见 `rework/ddraw.ini.orig`。

如果 `noactivateapp` 不够，下一个候选是 `hook_peekmessage=true`（cnc-ddraw 接管消息泵）。

### 顺带确认的一件事

游戏会**主动抢回前台**：`FUN_00541d10` 里 `GetForegroundWindow()` 发现自己不是前台时，
会调 `SetForegroundWindow(hwnd)` 把焦点夺回来。这是 2003 年那批 DirectDraw 游戏为了
保住输入捕获常见的手法，也是"手动点别的窗口后焦点又跳回游戏"的原因。

## 2. `zy/idx.lib`：全局条目编号空间

`idx.lib` 只有 218 字节，是纯文本：

```
num=14
name=Spr
name=Res00
name=ResPrior
name=ResPlayer1
name=ResBoss
name=ResNpc2
name=ResJM
name=ResPlayer2
name=ResPlayer3
name=ResNpc3
name=ResExNpc1
name=ResExPlayer1
name=ResExPlayer2
name=ResEx01
```

引擎把这 14 个库的条目表**首尾相接拼成一个全局编号空间**，BugLog 里的
`Init CombineLibEnd` 就是这一步。代码证据 `FUN_005054d0`：

```
读 ini 整数（num）              -> FUN_004e8670(.., &DAT_005757f0, ..)
分配 num * 0x910 + 4 字节       -> 每个库一个 0x910 字节的描述符
循环 { 读 ini 字符串 name=      -> FUN_004e8540(.., &DAT_005757e8, ..)
       拼 "%s%s.lib"           -> s__s_s_lib_0057579c
       打开并挂到描述符上 }     -> FUN_00506fe0
```

对应的全局基址（`tools/rekit/find_tables.py --list` / `analyze_graphid.py` 可复算）：

| # | 库 | 全局范围 | 条目数 |
| --- | --- | --- | --- |
| 1 | `Spr` | 0 .. 1789 | 1790 |
| 2 | `Res00` | 1790 .. 16130 | 14341 |
| 3 | `ResPrior` | 16131 .. 17220 | 1090 |
| 4 | `ResPlayer1` | 17221 .. 22468 | 5248 |
| 5 | `ResBoss` | 22469 .. 23670 | 1202 |
| 6 | `ResNpc2` | 23671 .. 26344 | 2674 |
| 7 | `ResJM` | 26345 .. 28527 | 2183 |
| 8 | `ResPlayer2` | 28528 .. 34759 | 6232 |
| 9 | `ResPlayer3` | 34760 .. 38727 | 3968 |
| 10 | `ResNpc3` | 38728 .. 40245 | 1518 |
| 11 | `ResExNpc1` | 40246 .. 42427 | 2182 |
| 12 | `ResExPlayer1` | 42428 .. 43587 | 1160 |
| 13 | `ResExPlayer2` | — | 0（空库，只有 256 字节头） |
| 14 | `ResEx01` | 43588 .. 46526 | 2939 |

合计 **46527** 个条目。

> `ResJM.Lib` 带语言后缀（`.Lib.chs/.cht/.eng/.jpn`），解析时按 `%s%s.lib`
> 的拼接顺序会命中 `ResJM.Lib.chs`。

## 3. 图形ID 是 `SprRole` 的角色编号，**不是** `Spr` 的条目下标

> **本节结论已被后续修正。** 当时我统计出"`图形ID` 的取值都落在 0..1789
> （`Spr` 的条目区间）"，于是当成"Spr 条目下标"。拿到 `slr.fol` 里的 `SprRole.h`
> 之后才确认：`图形ID` 是**角色编号**，条目下标是宏的**值**，两者是不同的命名空间，
> 只是数值范围恰好重叠。

`bdh/chs/Role.txt` 第 5 列 `图形ID`，去掉哨兵值 `9999` 后共 **149 个不同取值**，
它们**恰好等于** `SprRole.h` 里 150 个角色编号去掉孤儿 `435`
（`tools/rekit/analyze_graphid.py` 可复算：交集 149，"仅角色编号有" 只有 435）。

所以：
- `剑客` → 图形ID **901** → 去找 `SPR_ROLE_901_*` 那 82 条定义
  （`901_CA_001_001`=34、`901_HD_001_001`=112、`901_TK_001_001`=114…），
  这 82 条才是剑客的身体部件
- `Spr#901`（**条目下标** 901）与角色 901 **无关**，它是一条旋转刀光效果表
- "把 `图形ID` 当 `ResPlayer1` 下标"这个更早的假设同样是错的，但和本条是两回事

## 4. `Spr` 的条目不是图片，是动作描述表

对 `Spr` 抽样（`tools/rekit/probe_spr.py`、`contact_sheet.py`），条目既不是 `lep`
也不是帧包，而是二进制记录表。头部前 4 个双字大致是
`[数量, 数量?, 4, 7]`，其中 `4` 与 `7` 在**所有**抽样条目里恒定（版本/格式标记）。

`Spr#901`（剑客）完整解析：

```
1924 字节 = 4 + 48 × 40
+0x000  u32 count = 48
然后 48 条 40 字节记录（首条从 +0x004 开始）：
  +0  1        (恒定)
  +4  4        (恒定)
  +8  7        (恒定)
  +12 0        0
  +16 4        4
  +20 ref      0x00101737, 0x00101738, 0x00101739 ... 每条 +1
  +24 0
  +28 0
  +32 a        36, 33, 28, 22, 21, 30, 37, 40, 41, 39 ...
  +36 b        26, 29, 31, 31, 30, 30, 30, 28, 25, 27 ...
```

`(a,b)` 平滑变化，像**逐帧的裁剪偏移或尺寸**；`ref` 每条加 1，像**逐帧递增的图片引用**。

对照条目：`Spr#0` 240 字节 = 16 + 8×28（头部 4 双字，记录 28 字节）；
`Spr#5` 25732 字节，首双字 128；`Spr#655` 135220 字节，首双字 656。
**至少存在两种记录长度**，说明记录里带变长部分，不能只按首双字除。

### 引用编码（已从代码确认）

`FUN_005051e0` 是引擎"把编号解成运行时对象"的统一入口：

```c
uVar6 = param_1 >> 0x18;                                    // 高位字节 = 帧/子图选择
iVar3 = *(int *)(*(int *)((int)this + 4) + (param_1 & 0xfffff) * 4);   // 低 20 位 = 全局条目号
...
if (uVar6 == 0) return **(undefined4 **)(iVar3 + 0x28);      // 取第 0 个子图
return *(undefined4 *)(*(int *)(iVar3 + 0x28) + -4 + uVar6 * 4);  // 取第 uVar6-1 个
```

即一个 32 位引用 =
**bits[19:0] 全局条目号**、bits[23:20] 标志、**bits[31:24] 帧序号**。

所以 `0x00101737` 去标志后是 `0x1737 = 5943` → 全局 5943 → `Res00` 本地
`5943 - 1790 = 4153`。实测 `Res00#4153..4200` 是一串**碎片**（衣角/刀光一类），
不是整套动作，说明"一条记录 = 一整帧"的解读**还不完整**，或者 `ref` 携带的
标志位还有别的含义（`0x0010` 这一位在 `177`/`655` 等条目里换成 `0x15`/`0x17`）。

### 运行时验证：文件字节不在内存里

用 CE 在游戏内按 AOB 搜 `Spr#901` 头部 24 字节 → **0 命中**；
再搜连续三条 `ref`（`37 17 10 00 38 17 10 00 39 17 10 00`）→ **0 命中**。

结论：引擎把 `Spr` 条目**解析成运行时结构**后才留在内存里，磁盘布局和内存布局不同。
要确定字段语义，必须在运行期抓一次解析结果（见下节）。

## 5. 下一步：用 F6 热键在 CE 里抓一次

静态读记录已经到极限了，给用户的方案（用户提出、也确实能绕开抢焦点问题）：

1. 我在 `Spr#901` 解析路径上下**一个**窄断点（或直接在解析函数返回后 dump 结构体）；
2. 用户按 **F6** → CE 的 Lua 装着断点并立刻把焦点还给游戏；
3. 断点命中时由 CE 的 Lua 回调**自动记录 + 继续**，全程不弹窗、不抢焦点；
4. 用户再按 **F6** → 摘断点、把记录写成文件；
5. 我离线读文件。

关键前提：断点要打在**解析 Spr 的那个函数**上，而不是每帧几百次的热点导入函数上
（之前把断点打在 `timeGetTime` 上就是因此把游戏搞崩过两次）。

在此之前，静态上可以先做：把 `Spr` 全部 1790 个条目按"首双字/尺寸"聚类，
找出所有变长记录的形状，等运行期数据一到就能立刻对上。
