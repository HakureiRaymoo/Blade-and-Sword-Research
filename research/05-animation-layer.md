## 1. ~~`Role.txt` 的列值是「库条目号」~~（已被推翻，见文首）

| `战休1` | 16*0*272*224*464*159 | 战斗待机 = 一组候选条目（随机取一个） |
| `平时走路` | 48 | 行走 = 条目 48 |
| `战斗走路` | 48*32*64 | 战斗行走 = 三个候选 |
| `跑步` | 80 | 跑步 = 条目 80 |
| `初始态` | 0 | 初始姿态 = 条目 0 |
| `挨打` | 112 | 受击 = 条目 112 |
| `硬直` | 96*144 | 硬直 = 两个候选 |
| `浮空` | 128*4 | 浮空 = 条目 128、4 |
| `防守` | 352 / `起身` 384 / `死亡` 400 | 各自对应条目 |

也就是说：**每个动作编号直接就是 `ResPlayer1.lib` 的条目下标**，19 个数字全部落在 0–400 区间内，与库容量吻合。

这一步的实际价值：资产导出器现在可以按"动作名"给每个帧包命名，而不是 `00016_000.png` 这种序号。

## 2. 角色是分层 + 分朝向的

把条目 0–23 的首帧排成联系表，**24 个全是腿**，姿势各异（走、跑、踢、跳）。

- 条目 16 与 17 都是 8 帧、53×36，几乎同尺寸 —— 不是「腿 + 躯干」，而是**同一动作的两个朝向**（叠加后是一堆交叉的腿，不是完整人形）。
- 条目 14/15（8 帧 44×44）、18/19（8 帧 17×56）也都是成对出现，同样符合同动作不同朝向。

所以单个条目 = **某动作 × 某朝向 × 某一层**。分层推导的直接后果：合成一个完整角色需要把同一帧号的多层按固定原点叠起来 —— 这个原点就是我们要找的锚点。

## 3. 帧包里没有隐藏的偏移表

把 `split_bundle` 拆分后的每一帧按 `lep` 自身结构算"解析消耗字节数"，与实际帧长逐一比对：

| 条目 | 帧数 | 帧 0 长度 / 解析消耗 | 末帧长度 / 解析消耗 |
| --- | --- | --- | --- |
| `ResPlayer1#0` | 32 | 2150 / 2150 | 2048 / 2048 |
| `ResPlayer1#16` | 8 | 2088 / 2088 | 1714 / 1714 |
| `ResBoss#2` | 32 | 8014 / 8014 | 7042 / 7042 |

**零剩余字节。** 帧包 = `count + offsets[] + frames`，没有尾随的 per-frame 偏移表。

## 5. 用截图验证资产管线（已成功）

`tools/rekit/match_frames.py` 用**带掩码的归一化互相关（NCC）**在截图里找导出帧，numpy FFT 实现，不依赖 OpenCV。

对 15 张连拍（间隔 150 ms）做匹配，候选模板来自条目 `0 / 16 / 17 / 32 / 48 / 64 / 80 / 112 / 272` 共 244 帧，过滤后 110 帧可用（面积 ≥ 600 px、方差 > 2000）：

```
s_0.bmp: e00032_021.png@969,724 (NCC 0.777)
s_1.bmp: e00032_021.png@970,725 (NCC 0.781)
s_2.bmp: e00032_021.png@972,727 (NCC 0.785)
...
```

结论：

1. **导出的 PNG 能在真实游戏画面里被定位** —— 整条链路（`leyiLib` → `lep` → RGB565 → PNG）对着实机画面验证通过。这是像素管线第一次拿到"和游戏一致"的硬证据。
2. 命中的 `entry 32` 正是 `Role.txt` 里"战斗走路"的候选之一，动作编号映射也一并验证了。
3. 相机**完全静止**（背景位移 dx=0, dy=0，MSE 0.0），所以画面里的变化只来自角色自身。

## 6. 锚点实验：两次尝试都失败，原因不同

**第一次（待机连拍，15 张）**：相机完全静止（背景位移 0，MSE 0.0），但命中的始终是同一帧，位置抖动 5 px。待机帧彼此几乎相同，NCC 曲面很平，5 px 就是噪声本身，不足以区分对齐规则。

**第二次（运动中连拍，40 张）**：角色在屏幕上大幅移动（x 850–1100，y 430–830），位置差被移动量淹没；相机位移估计也随之失效。

**根因**：模板只有**单层**（腿）。腿在画面里表现为「深色布 + 白色绑带」的一小片区域，而这张地图上到处是深色岩石和草丛，NCC 0.72–0.78 在这类纹理上没有区分度——放大检查发现最佳匹配落在了石头上，而不是角色身上。

![匹配落在石头上的反例](../../out/probe/shadow_zone.png)

**结论**：用单层模板做屏幕定位不可靠。要测得锚点，必须先解决**角色分层合成**——知道哪几个条目组成一个完整角色、按什么顺序叠——才能拿完整人像做模板。顺序不能颠倒。

## 8. CheatEngine 桥（已打通）

沙箱的低完整性令牌挡住的是 `OpenProcess`，挡不住 **loopback TCP**。`D:\Dev\sometools\mcp\cheatengine-mcp-bridge` 提供了一条现成的缝：

```
CE 内 Lua 桥  →  命名管道 \\.\pipe\CE_MCP_Bridge_v99  →  ce_tcp_relay.py  →  TCP 127.0.0.1:9876
```

中继由用户侧（medium 完整性）启动，我在低完整性下走 TCP 说话，于是拿到了**等价于 CE 的完整权限**：读内存、扫描、硬件断点（含寄存器与栈捕获）、`evaluate_lua`。

已封装：

| 工具 | 作用 |
| --- | --- |
| `tools/rekit/ce_client.py` | 长度前缀 JSON-RPC 客户端 + `lua()` 便捷方法 |
| `tools/rekit/attach.py` | 按窗口标题反查 PID（进程枚举在沙箱里被过滤），自动 `openProcess` + `debug_process`，并校验线程数 |

### 踩过的坑

1. **只 `openProcess` 不够**：进程打开了但 `get_thread_list` 返回 0，断点全部静默不触发。必须再调用 `debug_process` 才有线程表。
2. **PID 会变**：游戏崩溃重启后 PID 从 39700 变成 21016，CE 仍挂在旧 PID 上，表现为"断点装上了但永远 0 命中"。先对比窗口 PID 与 `getOpenedProcessID()` 能立刻发现。
3. **窗口标题会误伤**：按"刀剑封魔录"匹配会把 DSH 自己的窗口（标题里也有这四个字）认成游戏，`attach.py` 现在只认 `DaojianServer` / `ComeOn`，并排除 DeepSeek/Harness/Chrome 等。

验证：`timeGetTime` 上打硬件断点，0.5 秒内 188 次命中；`get_thread_list` 返回 29。

### 崩溃事故与断点使用规程

在一次运行中，游戏在切回前台时崩溃。最可能的原因是本仓库自己的断点用法：

1. `focus_probe.py` 一旦检测到游戏成为前台，就**立刻连下 6 个硬件断点**；
2. 更早还在 `timeGetTime` 上下过断点——它是每帧调用的 API，实测 **0.45 秒 897 次命中**，即约 2000 次/秒，每次命中都要跑一遍 Lua 回调（抓寄存器、入表、continue）；
3. 对象是 2003 年的 DirectDraw 程序，跑在 WOW64 上，外面还套着 dgVoodoo 的 D3D11 转译层。

三者叠加足以让这种老程序崩掉。因此定下规程：

- **不在 API 导入上下断点**，尤其 `timeGetTime` / `GetMessageA` 这类高频函数
- **不在获得焦点的瞬间自动下点**
- 一次只下一个断点，只挑窄小的游戏函数，持续时间 < 1 秒
- **优先用内存扫描 + 改值**，完全不碰调试器

`focus_probe.py` 已加 `--yes` 强制确认，默认拒绝下点。

### 致命障碍：CE 本身会抢焦点

用户观察到并确认：**CE 一执行操作就把前台抢走，游戏随之停住**。这解释了此前所有"断点装上了却 0 命中"的现象——采样时游戏早已不在前台，绘制分支根本不执行。

另外，CE 只要开着模态窗口（例如 `Cheat Engine settings`），桥接调用就会**超时**：模态对话阻塞了 CE 的 Lua 执行线程。

结论：在本机当前这套组合下（dgVoodoo 包装层 + CE 抢焦点 + 模态窗口），**硬件断点路线不可靠**，不作为主路径。

### 静态路线：窗口过程在哪里

- `RegisterClassA` 调用点 `0x542AB0`，`CreateWindowExA` 调用点 `0x5424DF`
- `DefWindowProcA` 全程序只有一处调用：`0x5427A5`（一个只转调默认过程的壳）
- `GetForegroundWindow` 调用点 `0x541D10`，该函数在检测到自己不在前台时**主动 `SetForegroundWindow` 抢回焦点**
- 运行时 `GetClassLongPtr(GCLP_WNDPROC)` 返回 `0x5A592D40` = **DDRAW.dll+0x22D40**，即 dgVoodoo 子类化了窗口，游戏自己的窗口过程不在链顶

因此"失焦停画"不是游戏单方面能修的：它要么在 dgVoodoo 那一层，要么需要改窗口过程链。


### 让游戏在后台继续渲染（待实施，方案为纯内存操作）

游戏失焦时逻辑仍在跑（`timeGetTime` 持续命中）但不进入绘制分支。计划：

1. 聚焦状态下扫描模块可写区里值为 1 的字节/双字，作为候选集
2. 失焦后 `next_scan` 搜值为 0 —— 两次扫描的差集里就有「活跃标志」
3. 把该标志固定为 1，或把判断处 NOP 掉

全程只读内存 + 写一个字节，不需要调试器，也就不会重演上面的崩溃。


## 9. 角色合成：库是按部件分段的

抽查 `ResPlayer1` 的 896–914 段与 `ResPrior`、`Res00`：

- **896–910 全是武器**（不同款式的刀剑，带刀柄、不同角度）
- 其中夹着**靴子**与**彩色菱形**（蓝/红/绿/黄，应是选取框或标记）
- `ResPrior`、`Res00` 同样以武器和标记为主

结论：资源库不是"一个角色一个段"，而是**按部件类型分段的扁平池**，角色由若干条目按同一帧号叠出来。这解释了为什么条目 0–23 全是腿：那是"腿部"这一段的连续动画。

下一步（CE 已就绪）：在绘制函数上打硬件断点，捕获一帧内所有绘制调用的 `(this, x, y, w, h)`，筛出落在角色屏幕位置附近的那几条——它们就是该角色的层清单，顺序即绘制顺序（也就是叠加顺序）。

## 10. 关于帧锚点（已解）

当时确认的三点是对的：不在 `lep` 头里、不在帧包里、运行时图像对象也没有原点字段。

**答案在组合表每一层的槽位上**：每个子图带 4 个 short，
绘制偏移 = `(A − C, B − D)`（`FUN_0050b3f0` / `FUN_0050b440`）。
`lep` 是紧裁过的，`C/D` 就是它的裁剪原点，所以"锚点"在数据里恒为 `(0,0)`。
完整推导与实测见 [07-runtime-capture.md](07-runtime-capture.md) §7。
